# Kilo Code 调用 Kimi K3：综合项目管理系统开发提示词

> 使用建议：在 Kilo Code 中选择 **目标模式**，选定 Kimi K3 后，将下方提示词整体粘贴。目标模式负责持续推进整个项目，并在实施和排错阶段使用编码、调试能力。

---

## 可直接复制的完整提示词

请使用目标模式执行本任务。你是一名经验丰富的产品经理、企业软件架构师、全栈工程师、数据工程师、测试工程师和 UI/UX 设计师。请在当前工作区内，为我从零设计并实现一个功能全面、界面优美、易于使用、可实际运行的中文“综合项目管理系统”。

我提供的 Excel 仅作为业务灵感和界面参考。你可以参考其中“项目明细、负责人、合同金额、应收回款、风险预警、团队效能、高管看板”等思路，但**不需要严格复刻工作表、字段、公式或页面布局**。请根据现代项目管理软件的最佳实践主动补充功能、优化结构；不要让 Excel 的局限限制系统设计。

最终成果不能只是需求文档、界面原型或演示页面，而应是一个前后端连通、数据库可用、核心流程跑通、经过测试、能按说明启动的完整项目。

## 一、产品定位

面向中小企业、项目制团队及管理层，建立统一的项目协作和经营管理平台，实现：

- 从项目立项到结项的全生命周期管理；
- 目标、任务、里程碑、进度和人员协作；
- 客户、合同、预算、成本、发票、应收和回款；
- 风险、问题、变更、审批和跟进；
- 工时、工作日志、文件和评论；
- 团队绩效、项目健康度和管理驾驶舱；
- 多角色权限、消息提醒和操作审计。

系统以中文为主，默认人民币和中国时区；桌面端体验优先，同时适配平板和手机。

## 二、用户角色

至少支持：

- 超级管理员：系统配置、组织、权限和全部数据；
- 企业管理员：本企业人员、部门、角色和基础配置；
- 高管/管理层：查看全局经营和项目战情；
- 部门负责人：管理本部门项目、人员和指标；
- 项目经理：创建项目、分配任务、控制进度和风险；
- 财务人员：合同、预算、发票、应收、回款和财务确认；
- 项目成员：处理任务、填报进度、工时、日志和评论；
- 客户/外部协作者：只访问被邀请的项目和指定内容；
- 只读访客：查看授权范围内的信息。

权限必须在服务端验证，支持菜单权限、功能权限和数据范围权限，不能只在前端隐藏按钮。

## 三、核心功能

### 1. 工作台与个人中心

- “我的工作台”：我的任务、今日到期、已逾期、待审批、待跟进、最近项目和通知；
- 快捷创建项目、任务、回款、风险和工作日志；
- 个性化快捷入口和常用筛选；
- 个人资料、通知偏好、主题和语言设置；
- 最近访问、收藏项目和操作历史。

### 2. 项目组合与项目全生命周期

- 项目组合、项目集和单项目三级管理；
- 项目模板；
- 立项申请、评审、启动、执行、验收、归档和结项；
- 项目编号、名称、客户、部门、负责人、成员、优先级、阶段、状态；
- 计划起止日期、实际起止日期、项目目标、范围和成功标准；
- 项目健康度、完成率、剩余天数、预算消耗和风险等级；
- 项目复制、归档、暂停、恢复和批量操作；
- 自定义字段、标签和状态流程；
- 项目概览页汇总进度、任务、里程碑、财务、风险、动态和附件。

### 3. 目标、任务和里程碑

- 项目目标和关键结果；
- 任务、子任务和多级任务；
- 负责人、协作人、关注人、优先级、状态、截止日期、预计与实际工时；
- 前置/后置依赖、阻塞关系和循环依赖检查；
- 检查清单、评论、附件、操作记录和 @成员；
- 周期任务、批量创建、复制、移动和导入；
- 里程碑与交付物；
- 看板、列表、甘特图、日历和时间线视图；
- 拖拽排序与状态流转；
- 任务逾期、即将到期和长期无更新提醒；
- 项目进度不得只靠“已完成任务数”计算，应支持任务权重、里程碑权重或人工确认。

### 4. 团队、资源和工时

- 部门、岗位、成员、技能标签和可用性；
- 成员负载视图，识别过载和闲置；
- 资源排期和跨项目占用；
- 工时填报、审批、退回和统计；
- 工作日志、日报、周报；
- 请假/不可用时间对资源计划的影响；
- 团队绩效仅用于辅助管理，避免用单一指标简单排名。

### 5. 客户、联系人和商机衔接

- 客户档案、联系人、信用等级和历史项目；
- 客户相关合同、回款、沟通记录和附件；
- 可选的商机转项目流程；
- 客户门户仅展示授权内容；
- 客户反馈、验收意见和满意度。

### 6. 合同、预算和成本

- 合同与补充协议；
- 合同金额、签署日期、生效日期、付款条件和附件；
- 项目预算、预算科目和预算版本；
- 人力、采购、差旅、外包等成本；
- 预算申请、调整、冻结和超支预警；
- 预算、实际成本、合同额、收入和毛利对比；
- 所有金额使用定点十进制，禁止使用浮点数。

### 7. 发票、应收和回款

参考 Excel 中的应收看板思路，但采用更完善的业务模型：

- 收款计划和阶段性付款节点；
- 应收日期、计划金额、账龄和逾期天数；
- 开票申请、开票登记、红冲和附件；
- 每日回款登记；
- 一笔回款可核销多个应收，一条应收也可被多笔回款核销；
- 回款草稿、财务确认、冲销和更正；
- 已收、应收、已开票未收、未开票应收和回款率；
- 银行流水号防重复；
- 超额回款、无项目回款和金额异常提示；
- 月度回款趋势、应收账龄、负责人应收敞口和高风险项目榜单；
- 风险榜单必须动态计算，不能硬编码项目；
- 财务流水不得随意物理删除，冲销和修改必须留下审计记录。

### 8. 风险、问题、变更和决策

- 风险登记：概率、影响、等级、责任人、应对方案和到期日；
- 问题单：严重程度、影响范围、处理状态和根因；
- 项目变更：范围、时间、预算、资源变更及影响分析；
- 决策记录：背景、备选方案、结论和参与人；
- 风险矩阵和风险趋势；
- 风险自动提示可结合：延期、逾期任务、预算超支、应收逾期、长时间无更新、资源过载；
- 每个风险等级必须显示判定原因，不能成为黑盒。

### 9. 审批流

- 支持立项、预算、合同、费用、开票、回款确认、项目变更和结项审批；
- 默认提供实用审批模板；
- 支持顺序审批、会签、或签、转交、加签、撤回和抄送；
- 审批流程可配置，但首期不要实现过度复杂的低代码流程引擎；
- 审批记录完整留痕。

### 10. 文档、知识和协作

- 项目文件夹、附件上传、预览、下载和版本记录；
- 评论、回复、表情和 @成员；
- 项目公告和动态时间线；
- 会议记录、决策记录和知识库；
- 文档权限继承项目权限，并支持单独授权；
- 文件类型、大小和安全校验。

### 11. 通知与待办

- 站内通知和待办中心；
- 任务分配、到期、逾期、评论、@提及、审批和风险提醒；
- 已读/未读、全部已读、按类型筛选；
- 允许用户设置通知偏好，避免重复骚扰；
- 邮件、企业微信、钉钉等外部渠道预留扩展接口，首期可不真实接入；
- 同一事件合并通知，设置免打扰时段。

### 12. 报表与管理驾驶舱

- 高管驾驶舱：项目数、合同额、回款额、应收额、预算、成本、利润、延期项目和高风险项目；
- 项目健康度分布；
- 项目阶段与状态分布；
- 月度立项、结项和回款趋势；
- 预算与实际成本；
- 部门、负责人和客户维度分析；
- 应收账龄和逾期趋势；
- 资源负载和工时趋势；
- 风险 TOP 10、延期 TOP 10、应收 TOP 10；
- 所有图表支持全局筛选和点击钻取；
- 指标显示统计口径和最后更新时间；
- 支持导出当前筛选结果。

### 13. 搜索、导入和导出

- 全局搜索项目、任务、客户、合同和文档；
- 搜索结果按类型分组；
- 支持 Excel/CSV 导入项目、任务、客户和回款；
- 导入步骤：上传、字段映射、预览、校验、确认、导入、结果报告；
- 导入必须支持逐行错误提示、部分错误修正和幂等处理；
- 可参考现有 Excel 自动识别项目编号、客户、负责人、合同金额、已收、应收等；
- 无编号合计行不得作为项目导入；
- 类似 `2024.06` 的月份值转换成标准年月；
- 导出必须遵守当前筛选和用户权限。

### 14. 系统管理和审计

- 企业、部门、用户、角色和权限；
- 项目状态、任务状态、优先级、风险规则和编号规则；
- 自定义字段和项目模板；
- 数据字典；
- 操作审计：操作者、时间、对象、动作、修改前后值；
- 登录日志、异常日志和系统健康检查；
- 数据备份和恢复说明。

## 四、数据设计原则

- 使用规范化关系模型，复杂多对多关系使用关联表；
- 项目、任务、合同、发票、回款等使用稳定主键；
- 业务编号与数据库主键分离；
- 重要实体保留创建人、创建时间、更新人、更新时间和版本号；
- 关键业务记录使用逻辑归档或冲销，避免物理删除；
- 金额使用 `Decimal/Numeric`；
- 日期和时间采用统一时区策略；
- 数据库建立唯一性、非空、范围和外键约束；
- 并发更新使用版本控制或可靠的冲突处理；
- 看板指标由后端统一计算，前端不得自行形成另一套财务口径。

## 五、技术实现

如果当前仓库没有既定技术栈，优先采用：

- 前端：React、TypeScript、Vite、Ant Design；
- 图表：ECharts；
- 服务端状态：TanStack Query；
- 后端：FastAPI、Pydantic、SQLAlchemy 2；
- 数据库：开发环境 SQLite，生产可切换 PostgreSQL；
- 数据库迁移：Alembic；
- 测试：Pytest、前端组件测试、Playwright 端到端测试；
- 质量工具：Ruff、类型检查、ESLint、Prettier；
- 提供 Windows 一键启动脚本；
- 可选提供 Docker Compose。

如果仓库已有成熟技术栈，应先检查并尽量沿用。采用模块化单体架构，首期不要无必要地拆成微服务。

## 六、界面与用户体验

整体风格应专业、清晰、现代、有企业管理系统的稳重感，但不要做成拥挤的传统后台。

### 信息架构

- 左侧主导航，顶部全局搜索和快捷创建；
- 首页优先呈现“用户现在需要处理什么”，而不是堆满图表；
- 项目详情采用概览 + 分页标签结构；
- 面包屑、返回路径和页面标题清楚；
- 高频操作在明显位置，低频高级设置渐进展示。

### 列表体验

- 支持搜索、组合筛选、排序、分页和批量操作；
- 表头吸顶，关键列固定；
- 用户可选择显示列、调整列宽、保存视图；
- 筛选条件同步到 URL，返回后保留；
- 金额右对齐并使用千分位；
- 状态同时使用颜色、文字和图标，不能只靠颜色；
- 行内快捷操作不宜过多，其余放入“更多”菜单。

### 表单体验

- 表单分组，提供合理默认值和字段联动；
- 项目选择器支持编号、名称和客户模糊搜索；
- 实时校验但不要在用户输入第一个字符时制造大量红色错误；
- 自动保存草稿或提供离开页面未保存提醒；
- 保存失败时保留输入并给出可执行的错误说明；
- 高风险操作显示影响范围并二次确认；
- 回款、预算和合同金额变动前展示变更后的关键指标预览。

### 状态反馈

- 完整提供加载、骨架屏、空状态、错误状态和重试；
- 操作显示保存中、成功或失败；
- 长任务显示进度，完成后提供结果报告；
- 空状态不仅写“暂无数据”，还应提示下一步可做什么；
- 页面显示数据更新时间；
- 弱网或重复点击不能造成重复提交。

### 可访问性与响应式

- 键盘可以完成主要操作；
- 表单有明确标签和错误关联；
- 颜色对比度合理；
- 手机端优先保证工作台、任务、审批、回款和项目概览可用；
- 大型图表在窄屏转换为可读卡片或横向滚动。

### 个性化

- 明暗主题；
- 收藏项目和常用视图；
- 可配置首页组件；
- 通知偏好和免打扰；
- 记住上次筛选与列表密度。

## 七、安全与可靠性

- 认证、授权和数据权限均在后端实施；
- 密码安全存储，会话和令牌遵循安全实践；
- 防止 SQL 注入、XSS、越权和恶意文件上传；
- 真实密钥只能放在环境变量，不得写入仓库；
- 提供 `.env.example`；
- 关键写操作使用事务；
- 创建回款、审批等接口支持幂等，防止重复提交；
- 审计日志不可被普通用户篡改；
- 提供数据库备份和恢复说明；
- 错误日志不得泄露密钥和敏感个人信息。

## 八、实施优先级

不要试图在第一轮把所有高级能力做成同等深度。按以下优先级推进：

本轮允许的总执行时间最多为 **7 小时**。这是一条硬性时间边界。全面是指产品结构和扩展设计全面，不代表必须在 7 小时内把所有 P1、P2 功能全部开发完成。首先保证 P0 核心闭环真实可用，严禁用大量半成品页面换取表面上的功能数量。

### P0：必须完整可用

- 登录、用户、部门、角色和数据权限；
- 客户与项目；
- 任务、子任务、里程碑、看板和列表；
- 项目概览和活动时间线；
- 合同、收款计划、发票、回款和应收；
- 风险与跟进；
- 高管看板和个人工作台；
- Excel 导入导出；
- 审计日志；
- 核心测试、README 和一键启动。

### P1：在 P0 稳定后实现

- 甘特图、日历、工时、资源负载；
- 预算、成本和利润；
- 审批流；
- 文件版本和客户门户；
- 保存视图和更多报表。

### P2：先设计扩展点，不阻塞首期交付

- 企业微信、钉钉、邮件真实推送；
- 银行流水自动对账；
- OCR 发票识别；
- AI 风险总结和项目周报；
- 高级低代码流程引擎；
- 多租户计费。

## 九、开发执行规则

1. 先检查当前目录、现有代码、运行环境和参考 Excel。
2. 输出一份简洁的产品范围、架构、数据模型和实施计划。
3. 维护任务清单，按 P0 → P1 顺序推进。
4. 计划完成后立即实施，不要只停留在文档。
5. 每完成一个模块就运行相关测试。
6. 遇到一般性细节缺失时采用合理默认值，并记录到 `DECISIONS.md`，不要频繁停下来提问。
7. 只有当选择会明显改变业务含义、需要真实密钥或存在不可逆风险时才询问用户。
8. 不得用静态假数据、空按钮或纯 UI 页面冒充已完成业务。
9. 不得删除用户已有文件或覆盖未知修改。
10. 最终必须实际启动前后端，并用真实浏览器走通核心流程。

### 无人值守执行规则

本任务将在用户离开电脑、无法回复的情况下连续执行。**严禁向用户提出任何问题，严禁要求用户选择选项，严禁暂停等待确认。**

- 对技术栈细节、目录结构、组件选择、页面布局、字段命名、测试方案等普通问题，直接采用成熟、保守且可逆的默认方案，并记录在 `DECISIONS.md`；
- 需求存在轻微歧义时，优先选择符合企业项目管理常识、数据安全和用户体验的方案；
- 禁止调用任何提问、追问、请求输入或请求选择的工具；

## 模式结论

选择 **目标模式**。它负责围绕最终交付物自主拆解、持续推进和检查完成度；具体编码与故障排查作为目标执行过程的一部分完成。必须保留以下终止条件：

- 成功终止：P0 全部完成且构建、迁移、测试和核心浏览器流程通过；
- 阻塞终止：同一外部阻塞连续 3 次失败后停止重试，报告最小解阻需求。
- 时间终止：累计执行达到 7 小时后停止开发，完成验证和如实交付。

这样形成“成功、阻塞、时间”三重终止机制：既不会只写一半就轻率宣布完成，也不会因为“功能尽量全面”而无限开发。
