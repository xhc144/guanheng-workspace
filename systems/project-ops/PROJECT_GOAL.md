## 二、最终目标

在当前工作区交付一套真正可运行的中文响应式 Web 系统，供一家软件公司统一管理：

- 客户、人员和部门档案；
- 合同、项目、参与人员及纸质/电子档案；
- 分期应收、发票、回款和金额分摊；
- 年度服务费、续费和到期提醒；
- 项目提成计算、待发放和已发放；
- 需求、任务、缺陷、迭代、版本、工时和验收；
- 按客户、人员、部门、项目、月份、票款状态等维度统计；
- 管理员、财务、部门负责人、项目人员等角色权限；
- 系统内通知和 SMTP 邮件通知；
- Excel 导入导出、审计日志和数据备份说明。

目标不是静态原型或只有首页的演示。所有核心业务必须接入持久化数据，能新增、查看、修改、作废、搜索、筛选和统计，并经过实际构建与自动化测试验证。

## 五、技术与架构约束

- 延续当前 Next.js、React、TypeScript 工程，不重新初始化或另建子项目。
- 保持单体全栈架构；前端页面、服务端操作和业务逻辑位于同一仓库。
- 当前开发环境没有 Docker，先保证 Node 直接运行。持久化优先使用适合当前 Node 运行时的 SQLite 方案；数据库访问集中在服务端并保留以后迁移 PostgreSQL 的清晰边界。
- 金额在数据库中使用定点数或“分”为单位的整数，禁止 JavaScript 浮点数直接计算财务金额。
- 所有跨表财务写入必须使用事务或具有等价原子性的数据库操作。
- 上传文件保存在非公开目录或对象存储，数据库只保存元数据；外部共享盘路径可以单独登记。
- 生产配置通过环境变量提供，不把密码、SMTP 授权码、会话密钥或真实客户数据提交到仓库。
- 页面以服务端数据为准，浏览器存储只能保存主题、筛选偏好等非权威状态。
- 桌面端以表格、组合筛选和批量操作为主；手机端使用摘要列表、抽屉筛选和分步表单。

## 六、业务模块和必须实现的行为

### 1. 登录、组织和权限

- 用户、角色、部门、部门负责人、在职状态和项目成员关系。
- 至少包含管理员、财务、部门负责人、项目人员四类角色。
- 管理员查看全部；财务查看并操作财务数据；部门负责人查看本部门；项目人员只查看本人相关项目和款项。
- 权限必须在服务端校验，不能只隐藏前端按钮。
- 登录、退出、会话过期、密码安全存储、首次管理员初始化和操作审计。

### 2. 客户档案

- 客户名称、简称、联系人、电话、地址、银行账号、开户行、开票抬头、纳税识别号和备注。
- 客户可产生多份合同和多个项目；客户详情能够看到全部历史消费、合同额、应收、已收、未收、发票和服务费。
- 支持中文名称、简称、联系人、合同号、项目名的全局搜索。

### 3. 合同、项目和档案

- 合同与项目分别建档并通过关联关系连接，支持一份合同对应多个项目、一个项目关联多份合同。
- 合同字段至少包括编号、名称、客户、签订日期、合同金额、状态和说明。
- 项目字段至少包括名称、客户、项目经理、部门、参与人员、开始/计划完成/实际完成日期和状态。
- 参与人员可有不同职责和提成点数。
- 电子档案支持上传文件或记录外部路径；纸质档案记录柜号、层号、盒号和备注。
- 档案类型包含合同、蓝图、验收报告、发票附件、回款凭证及其他文件。

### 4. 应收、发票和回款

- 合同下可建立任意名称的分期应收计划，例如首期款、蓝图款、实施款、验收款和其他款项。
- 每笔应收包含金额、计划日期、负责人、款项类型和备注。
- 一笔应收允许对应多张发票和多次回款；一张发票或一笔回款也允许按金额分配到多笔应收。
- 发票只做登记和附件上传，不直接连接税务开票平台。
- 发票字段至少包含发票号、开票日期、金额、税率/税额、客户、附件和状态。
- 回款字段至少包含到账日期、金额、客户、付款账户、收款方式、凭证和备注。
- 系统根据有效分摊金额自动得出未开票、部分开票、全部开票、未回款、部分回款、全部回款和逾期状态。
- 禁止超额分摊；并发或重复提交不得造成重复入账。
- 财务记录只能作废重录，不允许物理删除。

### 5. 服务费

- 项目可以手工转入服务费，也可以由项目完成、项目款收齐或合同约定日期触发。
- 每个服务周期保存起止日期、金额、负责人、应收、发票、回款和状态。
- 续费时生成下一服务周期和新的服务费应收，不覆盖旧年度记录。
- 首页和列表显示本月、未来30天、已逾期的服务费，并能按项目经理、客户和部门筛选。

### 6. 通用规则

- 规则具有草稿、测试、已发布、停用状态，由管理员发布版本。
- 支持业务事件触发、AND/OR 条件、字段比较、日期条件、加减乘除、最小/最大值和舍入。
- 支持生成服务费应收、生成提成计提、创建提醒和更新允许的业务状态。
- 禁止管理员输入任意 JavaScript、SQL 或网络请求。
- 发布前可选择样本数据测试并查看计算过程；历史执行保存规则版本、输入快照、输出和错误。

### 7. 提成

- 计提来源可选合同额、实际回款或项目结算额。
- 计算基数支持扣减税点、业务费、代理费和其他费用。
- 同一项目可有多人参与，每人点数不同；个人提成按基数和点数自动计算。
- 提成状态至少包含待计提、待满足条件、可发放、已发放、已作废。
- 可以设置必须收到蓝图款、实施款或其他指定款项后才能发放。
- 财务可勾选多笔可发放提成形成发放批次；个人可按月份查看已发和未发提成。

### 8. 研发管理

- 需求、任务、缺陷、迭代、版本和里程碑。
- 客户/项目关联、提出人、负责人、参与人、优先级、状态、计划时间、实际时间、预计工时、实际工时、延期原因、验收人和验收结果。
- 评论、附件、变更记录和状态流转历史。
- 按开发人员、客户、项目、迭代、版本、状态和延期情况统计。

### 9. 统计、提醒和导入导出

- 首页指标：合同总额、应收、已收、未收、逾期、已开票未回款、本月回款、服务费到期、可发提成和研发待办。
- 报表按客户、项目、人员、部门、月份、款项类型、开票状态和回款状态组合筛选。
- 报表可以下钻到明细并导出 Excel；统计金额必须与有效业务明细严格一致。
- 系统内通知必须可用；SMTP 配置存在时发送邮件，失败进入重试且不得回滚业务操作。
- 首版不接企业微信；保留清晰的通知通道边界，未来有企业应用凭据后再接。

## 七、界面要求

- 使用当前经营工作台视觉方向：深墨蓝/绿色、暖白背景、清晰层级、高密度但不过度拥挤。
- 不做营销页式 Hero、跑马灯、无意义渐变或干扰财务操作的滚动动画。
- 所有业务模块都必须从导航到达；按钮、表单和错误信息使用中文。
- 表单有明确标签、必填提示、错误说明和提交状态；失败后保留用户已填写内容。
- 状态不能只靠颜色区分；键盘焦点可见，交互控件满足基本触控尺寸。
- 至少验证 375px 手机宽度、平板和桌面宽度；手机端不得出现无法操作的横向宽表。
