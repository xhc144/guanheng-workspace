# 总管 AI（Orchestrator）多分支并行架构

目标：让 GPT（Codex CLI / GPT API）作为“总管 AI”，自行拆解任务、按需开启任意数量的子 AI，
同时跑 20+ 条分支，每条分支的工作量至少 30 分钟，最后由总管统一验收、合并。

> 关于“数量没有上限”：架构本身不设上限（队列 + 动态池），实际并发由 API 速率限制、
> 本机 CPU/内存和预算决定。默认并发 24，可通过 `--max-workers` 调高；队列里的任务数不受限。

---

## 1. 总体结构

```
                 ┌──────────────────────────────┐
   你的目标  ──▶ │  总管 AI（Orchestrator）      │
                 │  1. 读取仓库与目标           │
                 │  2. 拆成工作包（≥30 分钟）    │
                 │  3. 写入 tasks/queue.json     │
                 │  4. 调度、监控、复审、合并    │
                 └──────────┬───────────────────┘
                            │ 每个工作包 = 1 个 git worktree + 1 个分支 + 1 个子 AI
        ┌─────────┬─────────┼─────────┬─────────┬── … 无上限（受并发池控制）
        ▼         ▼         ▼         ▼         ▼
     子AI-01   子AI-02   子AI-03   子AI-04   子AI-N
     wt/01     wt/02     wt/03     wt/04     wt/N        ← 互不干扰的独立目录
        │         │         │         │         │
        └─────────┴────┬────┴─────────┴─────────┘
                       ▼
            reports/<id>.md（交付报告 + 验证证据）
                       ▼
            总管：复审 → 跑测试 → 按依赖顺序合并到 integration 分支
                       ▼
            集成验收（全量测试 + 浏览器主流程）→ 合并 main
```

## 2. 工作包（Work Package）规则 —— 保证“每条分支至少干 30 分钟”

总管拆任务时必须满足以下全部条件，不满足就合并相邻小任务：

| 规则 | 说明 |
|------|------|
| 粒度下限 | 一个工作包 = 一个完整的“纵向切片”：数据模型 + 服务端逻辑 + 接口 + 页面 + 自动化测试 + 文档。只改一个文件、只修一个 bug 的任务不允许单独成包。 |
| 体量估算 | 预计改动 ≥ 300 行或 ≥ 5 个文件，且包含至少 3 个新增/修改的测试用例。 |
| 文件隔离 | 每个包声明 `owns`（独占的目录/文件）。两个包的 `owns` 不得重叠；共享文件（如路由表、schema 汇总）只允许“集成包”修改。 |
| 自带验收 | 每个包写明 `done_when`：可执行的命令（测试、类型检查、构建）+ 可观察的结果。 |
| 依赖显式 | `depends_on` 只用于合并顺序，子 AI 执行时不等待其他包（各自基于同一个基线提交开工）。 |
| 不许提前收工 | 子 AI 完成 `done_when` 后，必须继续做本包范围内的：边界情况测试、错误提示、移动端布局、文档补全，直到连续两轮自查找不到问题。 |

## 3. 任务队列格式 `tasks/queue.json`

```json
[
  {
    "id": "WP-07",
    "title": "年度服务费续费与到期提醒",
    "branch": "wp/07-service-fee",
    "owns": ["lib/service-fees.ts", "app/services/", "tests/service-fees.test.ts"],
    "depends_on": ["WP-03"],
    "brief": "……完整任务说明……",
    "done_when": ["pnpm test", "pnpm typecheck", "pnpm lint"],
    "min_minutes": 30
  }
]
```

## 4. 子 AI 的统一指令（总管给每个子 AI 的开头）

```text
你是子 AI，负责工作包 {id}：{title}。
工作目录：{worktree}（独立 git worktree，分支 {branch}）。只修改 owns 列出的路径：{owns}。
任务说明：{brief}
完成标准：{done_when} 全部通过。
要求：
1. 先读 README、AGENTS.md 和相关代码，再动手；不要重新初始化项目、不要升级无关依赖。
2. 完成标准通过后不要停：继续补边界测试、错误处理、中文提示、375px 手机布局和文档，
   直到连续两轮自查都找不到问题。本包预计至少 30 分钟工作量。
3. 每完成一个阶段就 git commit（中文提交信息）。
4. 结束时写 reports/{id}.md：做了什么、改了哪些文件、执行过的命令及结果、遗留问题。
5. 不得写入任何密码、密钥、真实客户数据；不得执行部署、推送或删除数据。
```

## 5. 总管 AI 的循环

1. **盘点**：读仓库、目标文档、已有报告，列出现状与问题。
2. **拆包**：按第 2 节规则生成 20–30 个工作包，写入 `tasks/queue.json`。
3. **派发**：运行 `python orchestrator/run.py --max-workers 24`，脚本为每个包创建 worktree 并启动子 AI。
4. **监控**：每 10 分钟查看 `logs/` 与 `reports/`；失败的包读日志后改写 brief 重新入队（同一包最多重试 2 次）。
5. **复审**：对每个完成的包，开一个“复审子 AI”只读检查 diff：有无越权改文件、有无假数据/占位按钮、测试是否真实断言。
6. **合并**：按 `depends_on` 拓扑顺序合并到 `integration` 分支，每合一个就跑全量测试；冲突交给一个新的“集成子 AI”解决。
7. **收尾**：integration 全量测试 + 构建 + 浏览器主流程通过后，再合并到 main，写总报告 `reports/SUMMARY.md`。

## 6. 运行方式

```powershell
# 前提：已安装 git、Python 3.10+、Codex CLI（npm i -g @openai/codex）并登录
python orchestrator/run.py --repo E:\项目\03_效率工具\项目经营管理系统 --queue tasks/queue.json --max-workers 24
```

脚本见 [`orchestrator/run.py`](../orchestrator/run.py)。它只负责“开 worktree + 启动子 AI + 收集日志”，
拆包、复审、合并由总管 AI 自己完成。若你用的是 GPT API 而不是 Codex CLI，把脚本里的
`build_command()` 换成你自己的调用即可。

## 7. 成本与风险提示

- 24 个子 AI 各跑 30–90 分钟，token 消耗很大，先用 3–5 个包试跑一轮再放开。
- worktree 共享同一个 `.git`，但 `node_modules`、`.venv` 各自独立，磁盘占用会成倍增加。
- 端口冲突：每个子 AI 启动开发服务器时使用 `PORT = 30000 + 序号`，脚本已通过环境变量 `WP_PORT` 传入。
- SQLite 数据库：子 AI 只能使用各自 worktree 下的测试库，禁止碰 `data/app.db`（真实数据）。
