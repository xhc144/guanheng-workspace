## 并发验证：关闭与退出必须完成

原 worker 在 `postMessage` 后才 `finally db.close()`；父 Promise 收到消息即 resolve，后续异常退出不能撤销已完成的 Promise，验证 SELECT 可与关闭重叠。第一次原样全量测试 05 为105/105，这不能证明竞态已消失。

10 的受控真实 SQLite fixture 采用 EXCLUSIVE WAL 连接，并用 Atomics 固定“已提交/已发结果/尚未关闭”窗口：`isTransaction=false`，早读实际得到 errcode5 `database is locked`，释放关闭门并等 exit0 后同一 SELECT 成功。该 fixture 证明连接生命周期机制；不把受控锁模式说成已重新捕获历史每一次关闭内部锁的精确时机。

实际回款 worker 先取得业务结果，再成功 `db.close()`，之后发带 `closed` 实测值的结果。父线程只在 **exit=0 且确有合法结果** 后结算；error、非零退出、缺结果、重复或无效消息都会失败。真实两个连接仍经同一屏障抢100000分应收、各回款60000分：一笔成功、一笔超过应收余额；回款/审计/幂等各一条、分摊60000分的全部原断言保留，并增加已关连接/已退出断言。原15秒测试预算和 worker busy_timeout5000未改，验证连接没有增加等待、重试或 busy_timeout。

新增回归固定晚关闭窗口，结果消息到来时 Promise 仍须 pending；异常退出/无结果也须拒绝。17 暂恢复“收到结果即 resolve”，新回归实际失败；随后恢复字节。测试直接验证真实锁/实际查询及退出顺序，没有靠多轮自然竞态重跑碰绿。
