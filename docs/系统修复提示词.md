## 三、已知问题（我在本地核实过，你要在仓库里复查确认）

1. systems/project-ops/package.json 里 next、react、react-dom、lucide-react、@types/* 等依赖写的是 "latest"，重新安装就可能装到不兼容的版本，导致构建失败。AGENTS.md 也提醒这个 Next 版本有破坏性改动。
2. systems/pms-suite/使用说明.md 里写死了旧路径 E:\项目\应用项目\…，但文件夹早就搬走了；start-helper.ps1 直接调用 .venv\Scripts\python.exe，仓库里没有虚拟环境，也没有自动创建的步骤，所以一键启动在任何新机器上都会失败。
3. pms-suite 的默认账号互相矛盾：DeepSeek版/backend/app/main.py 和测试里用 Admin@123456，但 DeepSeek版/backend/app/seeder.py 和 ASSUMPTIONS.md 写的是 admin123；三个版本的 API 前缀也不一致（/api 和 /api/v1）。
4. DeepSeek版/backend/app/config.py 里 SECRET_KEY 有硬编码默认值，生产环境没配置时会直接拿这个值启动。
5. DeepSeek版 的 FINAL_STATUS.md 和 IMPROVEMENTS.md 自称“114 项改进全部完成、验收全通过”，但没有任何可复现的证据，不能当真。
6. 最大的问题：pms-suite 和 project-ops 在客户、合同、应收、发票、回款这些功能上大面积重叠，公司现在同时维护着两套系统。
7. 业务口径未确认：需求口述里出现了“暑期款”“运输款”“千万合同”等疑似听写错误的词，部分财务状态和提成规则无法唯一解释。
8. company/投标方案生成服务/方案生成服务/ 依赖的 templates/base-v3.pptx 和 templates/manifest.json 含客户信息，没有放进仓库（见 templates/README.md）。代码里的客户识别词已经换成“模板客户”“示例地区A”等占位词，所以这个服务在仓库里没法完整运行；微信支付也还没接入。

## 四、最终目标

1. 以 systems/project-ops 为唯一主线，不另起新项目。
2. 把 pms-suite/DeepSeek版 里主线没有、但对关衡有用的功能用主线技术栈重写进主线：里程碑/甘特图、工时与资源负载、风险与审批流、预算与成本利润、客户门户（参考 DeepSeek版/frontend/src/pages/ 和 backend/app/routes/）。不要把 Python 代码直接搬进来。
3. 在主线里新增关衡特有的模块：商机与投标管理（中标后一键转成合同和项目），以及关务实施模板（加工贸易 / AEO 项目的标准阶段和交付物清单）。
4. pms-suite 修到“新机器上能一键启动、能登录、文档和实际一致”，然后标记为归档参考版，不再继续开发。
5. 主线必须向后兼容现有数据库结构：只能新增表和字段，并且要写幂等迁移（pnpm db:seed 可以重复执行），因为线上真实数据库会直接升级。

## 五、执行流程（只靠 GitHub 完成）

第 1 步 盘点：在分支 orchestrator/plan 上实际安装依赖、运行各系统的测试和构建（project-ops：pnpm install、pnpm test、pnpm typecheck、pnpm lint、pnpm build；pms-suite：各版本 pip install -r requirements.txt 后跑 pytest，前端 npm ci 和 npm run build）。把“文档声称的”和“实际跑出来的”逐项对比，写进 reports/00-盘点.md，附命令和输出摘要。

第 2 步 拆包：按第六节的清单拆成 20–30 个工作包（可以合并或调整）。每个工作包必须同时满足：
- 是一个完整的纵向切片：数据 + 逻辑 + 接口 + 页面 + 测试 + 文档；预计至少 30 分钟工作量，至少改动 5 个文件，至少新增 3 个真实断言的测试；
- owns 写明独占的路径，不同工作包的 owns 不得重叠；共享文件（数据库 schema 汇总、导航菜单、路由表）只允许由一个专门的集成工作包修改，其他包把需要改的地方写进各自的报告。
写入 tasks/queue.json（字段：id、title、branch、owns、depends_on、done_when、min_minutes），并为每个包写一份 tasks/WP-XX.md：这份文件就是交给子 AI 的完整指令，必须自成一体，不能写“见上文”。

第 3 步 建集成分支：从 main 建 integration 分支，把 orchestrator/plan 合并进去。

第 4 步 并行派发：每个工作包交给一个子 AI，各自从 integration 新建分支 wp/XX-简称，完成后向 integration 提 PR，标题以“[WP-XX]”开头。
- 如果你能自己开子任务、子代理或并行 Codex 任务，就同时开 20 个以上，一个工作包一个；
- 如果不能，就在这一步停下，给我一份清单，每行一句可以直接粘贴的启动指令，格式是：“在仓库 xhc144/guanheng-workspace 的 integration 分支上，完整执行 tasks/WP-XX.md”。我会逐个开新任务执行。

第 5 步 复审与合并：每个 PR 由你或一个只读的复审子 AI 检查：有没有改出 owns 范围；有没有占位按钮、假数据或空实现；测试是不是真的在断言；有没有写入密钥或真实客户信息；有没有加二进制文件。通过后按 depends_on 顺序合并进 integration，每合并一个就跑一遍全量测试和构建；合并冲突交给新的集成子 AI 处理。

第 6 步 验收：integration 上 pnpm test、typecheck、lint、build 全部通过，并且“建客户 → 建合同和分期应收 → 开票 → 回款 → 看报表 → 计提成 → 服务费续期”这条主流程有自动化测试覆盖（环境支持浏览器的话，再用 375px 和桌面宽度实际走一遍），然后写 reports/SUMMARY.md，提 integration → main 的 PR，由我来合并。
